# 案件、發包、收付款與 YUSHI 資料連動規則

版本：2026-09-10。供發包登記、報價匯入、收付款 Skill 及後續網站整合共用。這是操作契約，不代表新欄位、跨入口交易服務或網站發包功能已實作。

## 共用原則

- 資料主檔在既有 Notion；案件頁是檢視入口，不維護第二套發包金額。
- 發包合約額、实际收付款、會計認列是不同事件。只確認發包不寫實付或銀行分錄。
- 使用者清楚授權的登記先摘要後執行；只詢問會影響案件、金額、稅別、交易性質或帳戶的缺漏，不因每一步都有寫入而重複確認。
- 金額按來源幣別與精度，NTD 整數款用整數加總。未知不是零；不猜稅率、不用 AI 示意數字記帳。
- 讀取最新 schema 與完整關聯／分頁；rollup/formula 參照需解析或由完整明細重算，不能拿參照字串判斷餘額。保留原關聯，新增時合併去重；自動雙向 relation 已完成時不再盲寫另一側。
- Notion 工具傳 structured JSON；需要腳本時用 UTF-8 檔案與官方 API／SDK，不以 shell 插值拼中文或憑證。工具及 schema 以當次為準，歷史 API 故障只作排錯參考。

### 必須使用的 relation

| 寫入端 | 欄位 | 目標／驗收 |
|---|---|---|
| 發包管理 | 專案 | 案件；案件的發包項目包含該筆，成本 rollup 納入 |
| 付款明細 | `Related to 發包管理  (付款明細)` | 主發包；兩個空格，對應已付金額的雙向關聯 |
| 收款記錄 | `Related to 案件財務管理 (收款紀錄)` | 案件；已收金額 rollup 納入實收金額 |
| 分錄 | 關聯案件 | 本筆分錄對應的唯一案件 |
| 分錄 | 關聯發包付款明細 | 本次付款所建立的全部分攤明細 |
| 分錄 | 關聯收款紀錄 | 本次沿用或建立的收款排程 |

付款明細的單向 `發包項目` 不取代雙向欄位；另有一個單空格同名 relation 指向其他 data source，也不能使用。若欄位改名，以目標 data source、反向欄位及 rollup 關係辨識，不凭相似文字猜。

## 發包契約

輸入：operationId、案件 ID、供應商識別、工項、來源報價／版次或口頭確認依據、含稅成交額、稅別依據、可確認的發包日期、工程進度、原約／獨立追加／改約意圖。

現有欄位映射：標題→廠商名稱；案件→專案；工項分類→工種；含稅成交額→成本；確認發包→是否已發包；來源 PDF→報價單連結。其他尚無欄位者記入備註，保留 `YUSHI-AWARD:<operationId>` 與來源識別。

單純發包只有主發包記錄、案件關聯與檢視／歸檔；沒有收付款明細及現金分錄。成功結果包含 awardPageId、projectId、amountIncludingTax、operationId、檢視與歸檔結果；後兩項失敗時分別標 pending，不宣稱全部完成。

## 收付款計算及狀態

每筆收付款輸入必須包含：operationId、實際日期、金額、來源交易識別或說明、收／付方向、案件、實際帳戶、是否沖既有應收／應付、付款分攤或收款排程 ID。付款金額不可由發包成本自動代填為已付款；使用者明說「付清剩餘款」時可先由已核對餘額取得並摘要。

| 計算 | 規則 |
|---|---|
| 付款後累計 P | 原有效付款明細合計 P0 ＋ 本次該發包分攤 A |
| 合約未付 | 已核定含稅發包額 C − P；是合約餘額，不直接等同到期應付 |
| 付款狀態 | P=0 未付；0<P<C 部分付；P=C 付清；P>C 超付待核對，執行前先處理原因 |
| 收款後累計 R | 既有排程實收 R0 ＋ 本次收款 A，不以 A 覆蓋 R0 |
| 排程未收 | 核定應收 E − R；R<E 部分收、R=E 已收、R>E 先核對，不改應收額湊平 |

零元或負額、退款、扣款、退票、保留款釋放等不能套普通正額收付款；先確認事件與對應更正方式。使用者已明說訂金／分期且金額不超過餘額，不因小於總約額再次詢問。同額同日不等於重複，需看事件識別。

### 既有欄位相容方式

現在主發包 `狀態` 混用工程與付款，尚無獨立工程狀態、付款狀態欄位。保留現有 schema：部分付款用 `已部分付款`、付清才用 `已付款`；`是否已撥款` 在此流程只於付清時為 true，部分付為 false。原工程進度先保存在備註且不抹除既有內容。手勾已撥款但明細不符時先核對，不用勾選框推算付款。

若未來新增獨立欄位，工程狀態只由工程事件更新，付款狀態依累計計算；網站與 Skill 同步切換後才能停用舊欄位。此次不新增／刪除／改名正式欄位。

## 交易連動與帳戶

付款：每個發包分攤一筆付款明細 → 一笔該案件的總額分錄，關聯所有本次明細與案件 → 讀回成功後更新付款狀態。分攤總額必須等於本次交易，不能每個分攤都記一次總額。

一筆銀行付款跨案件時，現有單案件交易流程不能直接處理；先明確拆分各案金額與共用銀行交易參考，確認總額一致，再分案登記。不能將全額分錄掛多個案件讓各案都加總全額。使用者可一次交代多筆，各筆保留獨立結果。

收款：優先沿用已有排程，累加實收 → 每次實際收款一筆分錄，掛同一排程與案件。沒有排程才建立，應收額若另有合約依據用該依據；未知排程總額不擅自設成本次收款並標全部收清。單一收款日期欄只代表最新收款日，歷次日期與金額由分錄保留。

科目用 ID 加最新名稱／分類核對：原「銀行帳戶」ID `39e7aebd-089f-8140-b697-ee214fe68a91` 已在 YUSHI 紀錄改名玉山銀行，不再按舊名建第二個科目。現金 ID `39e7aebd-089f-8171-b525-f97f1bdfdb78`。僅說匯款而有多個可用帳戶，須辨明實際帳戶。

認列模式依既有分錄／使用者確認的帳務方式：已掛應收／應付時沖原科目，未掛且已確認直接收付認列時用相應收入／支出科目；無法判定則列待確認。不把預付款、票據、股東代墊硬套銀行費用分錄。股東代墊須有確認的股東往來科目與支援該類交易的入口。

## 查重、写入與恢復

1. 寫入前準備穩定 operationId、輸入摘要／指紋與讀前金額、原關聯、已知結果 ID。重試保留同一 ID 和內容；變更輸入不能悄悄沿用旧 ID。
2. 查主記錄／來源明細／分錄的來源交易參考及操作標記。找到完整結果直接讀回返回；發現部分記錄先修復／查核，不能重建整筆。
3. 優先使用可正常驗證使用者的既有 YUSHI 交易入口。其 `finance_operations`、內容指紋及寫入鎖目前只保護經該入口的請求，不能聲稱 Notion MCP 也受保護。不可偽造驗證標頭、讀出／複製 secret 或直接呼叫內部函式繞過授權及鎖。
4. 發包尚無網站交易 action，可透過已授權 Notion 工具執行本 Skill。建前存本機操作紀錄到 `100_Todo/projects/yushi-finance-operations/<operationId>.md`（相對共用根目錄）；記事件、來源、前值與結果，不存憑證。把 UUID 放主記錄備註。這是可追溯恢復記錄，不是跨裝置鎖；若有同事件處理中紀錄先查核。
5. 收付款若必須直接操作 Notion，先取得可確認的單一寫入時段、檢查沒有處理中／待查核交易，並記錄相同操作資料與 `YUSHI-SKILL:<UUID>` 標記。無法核實交易鎖與並行狀態時，先完成輸入整理，交既有登入網站入口，不能在 MCP 私自重建收付款繞過去重。此限制來自直接寫入不參與網站交易鎖，不要求每筆例行登記重複批准。
6. Notion 不具跨庫原子交易。每步保存新 ID；逾時／不明回應標 `needs_review`，依原 UUID、來源和關聯查證寫入是否存在。不得只換新 UUID 重試、刪原分錄或自動解鎖；只重做已證實未執行的步驟。有限讀回仍未知就交付具體待查核項目。
7. 收付款驗收：明細累計、分錄借貸金額與科目、來源／案件關聯及帳戶／案件合計相符。讀前讀後的差額核對應排除其他並行交易；如有差異不自行改期初或補一筆調整帳湊平。

### 直接收付款寫入的可接受查核證據

只查「沒有相似 Notion 明細」或使用者說「可以再試」不足以解除交易狀態未知。先由已登入的網站讀取 `/api/finance` 的 unfinished 清單，並依原 UUID 查 `/api/finance?operation=<UUID>`；不得自行偽造網站的登入標頭。需查看 D1 鎖時依既有 `OPERATIONS.md` 的已授權維護程序處理，不只靠清單當下為空就宣稱取得排他鎖。

MCP 直接收付款僅在維護者已建立可驗證的寫入隔離（例如網站已暫停新寫入、原未完成操作已查核且無其他寫入者），或後續已實作參與同一交易鎖的受驗證入口時進行。此次沒有新增這些機制；無此證據則使用現有正常登入的網站交易流程。恢復部分交易须逐一核對原操作 payload、既有明細、分錄及累計，不能透過網站新增另一筆交易代替修復。一般使用者同意登記不等於要求停站維護，本 Skill 不自行暫停網站。
