# 廠商發包登記

中文入口「廠商發包登記」；Codex 可用 `$vendor-award-registration`，或直接以中文交代。共用來源位於本目錄，其他入口只引用，不複製流程。

**正常主入口是 [報價單輸入資料庫](../報價單輸入資料庫/SKILL.md)**：廠商先提供報價單，完成報價整理／建檔後，使用者確認發包才自動接續本流程。使用者不必再啟動第二個 Skill，也不必重填報價已取得的資料。若報價已在先前建檔，本次直接說確認發包，就取回該報價接續；尚未讀取的報價單先交報價 Skill，不跳過報價來源核對。口頭資料僅作使用者明確要求補登等例外，不能當預設主流程。

先讀 [資料連動規則](references/data-linkage.md) 的「共用原則、已核對資料來源、發包契約」。若同時登記已付款，再讀其中收付款段落並接續 [發包付款登記](../發包付款登記/SKILL.md)。本 Skill 登記的是已確認的發包，不是銀行付款操作。

## 1. 整理已確認的發包

報價建檔與發包決定分開：同工項可有多家候選，確認報價資料正確不代表選定廠商。只有使用者明確選定的廠商、工項及成交條件進入本流程；其餘報價留在報價資料中，不增加已發包成本。議價後使用核定成交額，保留原報價及版本供追溯。

解析案件連結／名稱、廠商、工項、成交金額與稅別、來源報價／版次、發包日期及工程進度。沿用已匯入的報價資料，不重建報價品項、供應商或文件中心頁。

- 寫入必要資訊：唯一案件、可辨識廠商與工項、確認發包的意思、可追溯的含稅成交總額。案件或稅別有歧義才詢問；不以制式「未稅」文字推翻使用者已確認的成交條件。
- 使用者只說「今天發包」可用當地今天；報價日期不當成發包日期。不確定日期保留待確認，不能自行回填今天作歷史發包日。
- 付款條件、保留款、文件路徑尚無資料時標待補；不是無條件阻擋已明確發包的原因。未提供銀行帳戶不影響單純發包。
- 先簡述案件、廠商工項、含稅金額、日期、來源及將建立／沿用的項目。明確的「請登記／確認發包」已授權寫入，不逐步重複請使用者確認。僅提供報價或說「考慮發包」不視為確認發包。

## 2. 定位與查重

讀取最新主發包與案件 schema、案件的全部發包關聯（處理分頁），核對候選記錄與來源報價。工具選擇依當次能力，不照舊工具名稱或歷史故障禁用目前工具。

- 相同案件＋廠商＋工項＋來源報價／版次＋本次發包事件，且資料相符：沿用，讀回驗證，不再新增。
- 同廠商有不同工項或使用者明說獨立追加：可新增，標題用工項／追加範圍區分。
- 改價或新版報價究竟「取代原約」還是「增加一筆」不清楚：先查原紀錄及已付款，再釐清；不因版次不同就自動累加成本。
- 疑似重複缺來源識別：列候選與差異，不能以換名字繞過查重。找不到來源報價但口頭發包已完整授權，可在備註記使用者確認的事件與範圍，產生穩定操作 UUID。

## 3. 寫入一筆主發包資料

使用資料連動規則的既有欄位，不猜新欄位。標題為 `{案件名稱}｜{廠商簡稱}{工項簡稱}`；同廠商追加加具體範圍，例如 `（入口追加）`。

填 `專案`、`廠商名稱`、`工種`、`成本`（含稅成交額）、`是否已發包=true`、工程狀態、可確認日期、來源報價連結及備註。`工種` 使用最新選項；非唯一對應才釐清，不私自新增 select。

備註保留來源報價識別、稅別依據、供應商 page ID（已找到時）、付款條件與待補事項、`YUSHI-AWARD:<UUID>`。供應商 relation 尚未存在時只記可追溯 ID／連結，不自動擴充正式 schema；人員型 `聯絡人` 不是供應商欄位。

新發包不建立付款明細、不勾已撥款、不建銀行收支分錄。沿用既有記錄時，保留付款明細及所有既有關聯，不清空狀態或備註，也不順手改名其他歷史記錄。

## 4. 案件正文必須看得到

讀案件正文及現有內嵌資料庫。優先沿用主發包 data source 的 linked view，核對 `專案 contains 本案 page ID` 篩選，再驗證這筆能顯示、其他案件被排除。僅有 relation 屬性不算完成此項驗收。

- 已有正確檢視：不再建表格；缺篩選時，在工具支援且可確定只影響本案檢視的前提下補篩選，不修改全公司主檢視。
- 沒有檢視：使用當次支援的 Notion 檢視工具建立本案 linked view；先查重，不另建獨立發包庫。
- 無法讀取／修改檢視：報告「主資料已建立／核對、正文檢視待處理」與記錄連結，保留待辦。不再自動補一份容易過期的靜態金額表；可建立 linked view 後再回來驗收。既有手工表不刪除，列為遷移待辦。

## 5. 報價單歸檔

若有已歸檔報價檔且是確認發包，依既有使用者規則移到同案名稱含「已發包」的資料夾。只在可確認的專案範圍內操作，保留檔名、檢查同名衝突，記錄移前移後完整路徑；目標不明才詢問。平台依當下 Windows／macOS，不寫死另一平台路徑。

移動後驗證檔案與分享連結仍可用，更新相關文件中心的歸檔路徑。僅有連結、無本機來源時不猜路徑，不假稱已移檔；回報待補。移檔失敗不重建已成功的發包記錄。

## 6. 讀回交付

確認主發包的案件 relation、工項、金額稅別、來源、操作標記；讀案件發包關聯及成本 rollup，正常新增應增加該筆成交額，沿用不得增加。公式參照未解析不當成 0 或聲稱核對通過。Notion 可能延遲，有限次讀回仍不符就標待查核，不重建。

回覆主記錄連結、案件／廠商／工項、含稅金額、工程狀態、正文檢視與歸檔結果；逐項區分完成與待補。涉及已付款才接付款 Skill，發包完成不代表已付款。
