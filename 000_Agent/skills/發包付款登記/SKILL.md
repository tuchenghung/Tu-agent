# 發包付款登記

先讀 [共用資料連動規則](../vendor-award-registration/references/data-linkage.md) 的共用原則、資料來源、收付款計算、交易連動及寫入恢復。欄位 ID、查重和交易規則只在該文件維護。

## 解析與定位

整理案件、廠商工項、本次實付金額、實際日期、付款方式、帳戶、分攤及來源交易參考。使用者明確交代已付款登記且資料齊全時，先摘要直接執行；不因本次是部分付款就再要求批准。

案件連結先追完整「發包項目」關聯，发包連結直接定位；只有名稱則搜尋並核對案件和來源，不憑廠商暱稱猜。多筆候選才釐清。找不到發包項目時，若使用者已清楚授權建立且發包資料完整，可先接 [廠商發包登記](../vendor-award-registration/SKILL.md)，再回本流程；否則只列缺漏。

付款金額不得直接拿「成本」當已匯款。使用者明說付清剩餘款，可由核對後的明細計算餘額並列摘要；僅說「匯款了」但缺金額，必須先取得金額。日期使用使用者指定或明確的今天，不為歷史交易猜日期。付款方式與實際帳戶須吻合，匯款不代表永遠是玉山銀行。

## 累計核對

取得發包核定含稅額 C、原有效付款合計 P0、本次分攤 A；計算 P=P0+A、合約未付=C-P。未知金額或勾選框與明細矛盾先核對。

- 明說分期／訂金且 A 不超過餘額：正常登記，不拿 A 與 C 比較後一律阻擋。
- 明說尾款：A 應等於目前餘額；不符才詢問原因。
- 未說明款項性質且金額與餘額有歧義，或超付／退款／扣款：釐清後再寫。
- 同案分攤不得重複發包 ID，總和等於本次付款；跨案照共用規則分案，不把總額重複掛案。

## 連動執行

先執行共用規則的操作識別、查重與寫入入口檢查。可用既有已登入 YUSHI 交易入口時沿用其 UUID／鎖，直接 Notion 路徑不得繞過未完成交易。未具備可核實的安全寫入條件時，交付完整待登記資料及原因，不宣稱已入帳。

1. 每個發包分攤建立一筆廠商付款明細：說明、付款金額=A、付款日期、付款方式及 `Related to 發包管理  (付款明細)`。備註記來源及操作標記，保留結果 ID。
2. 同案本次交易建立一筆總額分錄，填日期、摘要、交易類型「支出付款」、確認的借貸科目及相等金額、`關聯案件`、全部本次 `關聯發包付款明細`。已掛應付依原帳沖銷；未掛且已確認直接認列才用對應支出科目，不固定借工程款支出。
3. 讀回明細與分錄後，按共用規則更新累計付款狀態、是否已撥款、最新撥款日期。現有混合狀態欄位更新前保留原工程進度於備註，部分付款不勾付清。
4. 驗證發包已付=P、案件付款合計變動、本次分錄及帳戶變動；關聯完整才回報完成。任一步逾時按原 operationId 查核，不重跑整筆。

## 回報

列案件／廠商工項／本次付款／累計已付／合約未付／付款狀態，附明細與分錄連結、實際帳戶及操作結果。主資料已寫但分錄或讀回未完成，明列待查核而非「已付款完成」。

不更動業主已收金額，不把廠商匯款資訊建檔當實付；不重建案件正文手工金額表。檢視需要修正時由發包 Skill 的正文驗收流程處理。
