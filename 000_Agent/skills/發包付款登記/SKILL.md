## 為什麼查詢用存檔篩選、不直接吃 MCP 回傳

`mcp__notion-win__API-query-data-source` 目前環境會回 `invalid_request_url`（版本不相容），**不要用它查發包管理**。`API-retrieve-a-page`、`API-patch-page`、`API-post-page`（parent 用 `data_source_id`）這幾個基礎工具正常可用，優先用這些。

`API-post-search` 全域搜尋常回傳超大結果（曾一次 14 萬字元爆掉），若必須用：
1. 讓它把結果存成檔案（工具會自動存檔並回報路徑）
2. 用 Bash + `PYTHONIOENCODING=utf-8 python3` 讀檔、篩選標題關鍵字，寫出精簡結果到 scratchpad 再用 Read 讀
3. 不要對著原始 90K+ 字元結果做 Grep -o（沒有 -C 效果，因為 JSON 是單行）

## 執行步驟

### STEP 1：解析輸入 + 摘要確認 ⭐先摘要再動手

從使用者訊息抓：Notion連結（可能沒有）、廠商關鍵字、案件關鍵字、金額（可能沒有）、日期詞（今天/昨天/具體日期，預設當天）。

**支援一次多筆**（例：「正傑今天匯款龍潭1F8000及南港清潔15000」→ 拆成 2 筆分別處理）。

**在做任何 Notion 寫入之前**，先列摘要表格給使用者確認：

| 廠商 | 案件 | 金額 | 日期 |
|---|---|---|---|
| 誼能排水器 | 西湖辦公室排水修改工程 | 8,400 | 2026-07-15 |

- 若金額是從發包管理「成本」欄位帶入（使用者沒明講金額），表格備註「金額取自成本欄位，如非全額請告知」
- **使用者確認無誤後才進 STEP 2**；使用者說有誤就先修正

---

### STEP 2：定位發包管理記錄

先用 `API-retrieve-a-page` 抓使用者給的連結（若有），看 `parent.database_id`：

- **`parent.database_id` = 案件財務管理**（`2f97aebd-...`）→ 讀該頁「發包項目」relation 清單，逐筆 `API-retrieve-a-page` 比對廠商名稱關鍵字
- **`parent.database_id` = 發包管理**（`3337aebd-...`）→ 這頁本身就是目標，直接進 STEP 3
- **連結是廠商付款明細資料庫，或使用者沒給連結** → 用案件名稱關鍵字全文搜尋（見上方存檔篩選法），從結果中找 `parent.database_id` = 發包管理 的頁面，再比對廠商名稱

找到多筆疑似符合 → 列出來讓使用者選，不自己猜。完全找不到 → 停下來問使用者要不要提供更明確的連結或案件全名。

---

### STEP 3：金額比對——不符一律問，不設容許誤差

跟該筆發包管理記錄的「成本」欄位比對：
- **相符** → 視為全額付清，進 STEP 4
- **不相符**（不論金額較多或較少）→ **一律停下來問使用者**：是分期付款（訂金/尾款）、金額有誤、還是找錯記錄？不自動判斷、不設±誤差容許值

---

### STEP 4：更新發包管理記錄

```json
{
  "是否已撥款": {"checkbox": true},
  "撥款日期": {"date": {"start": "{日期}"}},
  "狀態": {"status": {"name": "已付款"}}
}
```

用 `API-patch-page` 寫入。**注意**：有時記錄可能已預先勾了「是否已撥款」但「撥款日期」是空的（表示使用者在 Notion 上手動勾過，但還沒補流程）——這種情況只需要補日期 + 走 STEP 5 建立付款明細，不用重複確認。

「狀態」若原本已經是比「已付款」更後面的階段，不要往回改（目前庫裡「已付款」是狀態選項中最終階段之一，通常不會有更後面的情況，但保險起見先讀現有狀態再決定）。

---

### STEP 5：建立「廠商付款明細」記錄（同步已付金額 rollup）

用 `API-post-page`，parent 用 `data_source_id: 3767aebd-089f-8109-a251-000ba7b6b948`：

```json
{
  "說明": {"title": [{"text": {"content": "{廠商}｜{案件名稱} 匯款{金額}"}}]},
  "付款金額": {"number": {金額}},
  "付款日期": {"date": {"start": "{日期}"}},
  "付款方式": {"select": {"name": "匯款"}},
  "Related to 發包管理  (付款明細)": {"relation": [{"id": "{STEP2找到的發包管理page_id}"}]}
}
```

**⚠️ 關鍵易錯點**：這個資料庫裡有兩個長得很像的 relation 欄位：
- `發包項目`（單向 relation，看起來也連到發包管理）——**不要用這個**，填了不會同步
- `Related to 發包管理  (付款明細)`（注意兩個空格，dual-linked）——**一定要用這個**，才會讓發包管理那邊的「已付金額」rollup 自動從 0 更新成實際金額

寫完後可以 `API-retrieve-a-page` 回頭確認發包管理記錄的「已付金額」rollup 是否已經等於金額，確認同步成功。

付款方式預設「匯款」，使用者說現金/支票/轉帳/票據則對應改成該選項。

---

### STEP 5.5：同步建立 YUSHI 分錄紀錄 ⭐串接銀行收支帳

在 `YUSHI 分錄紀錄`（data_source_id `39e7aebd-089f-8174-906b-000b60f80cc2`）新增一筆：

```json
{
  "摘要": {"title": [{"text": {"content": "{廠商}｜{案件名稱} 匯款{金額}"}}]},
  "日期": {"date": {"start": "{日期}"}},
  "交易類型": {"select": {"name": "支出付款"}},
  "借方科目": {"relation": [{"id": "39e7aebd-089f-816a-b446-ce49be49f58d"}]},
  "借方金額": {"number": {金額}},
  "貸方科目": {"relation": [{"id": "39e7aebd-089f-8140-b697-ee214fe68a91"}]},
  "貸方金額": {"number": {金額}},
  "關聯發包付款明細": {"relation": [{"id": "{STEP5建立的廠商付款明細page_id}"}]}
}
```

- 借方科目固定用「工程款支出」（`39e7aebd-089f-816a-b446-ce49be49f58d`）——目前發包記錄大多是直接付款、沒有先掛應付帳款，故直接借記費用
- 貸方科目固定用「銀行帳戶」（`39e7aebd-089f-8140-b697-ee214fe68a91`）——因為此 skill 觸發詞是「匯款」，付款方式若使用者明講是「現金」，貸方科目改用「現金」科目（`39e7aebd-089f-8171-b525-f97f1bdfdb78`）
- 若使用者特別說明這筆之前已經掛過「應付帳款」（少見情況），借方科目改用「應付帳款」科目（`39e7aebd-089f-81b0-84ef-e2f11f831133`），沖銷負債，不要記費用
- 若使用者說明是「老闆/股東自己墊錢付的」，貸方科目改用「股東往來」科目（負債增加，代表公司欠股東錢），不是銀行帳戶

寫完後可以再讀一次「工程款支出」與「銀行帳戶」科目頁面的「目前餘額」，確認 rollup 有正確累加（工程款支出借方增加、銀行帳戶貸方增加、餘額對應變動）。

## 重要規則

1. **先摘要、後動手**：任何 Notion 寫入前，必須先把「廠商/案件/金額/日期」整理成表格給使用者確認
2. **支援一次輸入多筆**，逐筆各自跑完整 STEP 1~6
3. **金額不符發包成本一律停下來問**，不設誤差容許範圍，不自己判斷是分期還是打錯
4. **relation 欄位別填錯**：廠商付款明細寫入時務必用 `Related to 發包管理  (付款明細)`，不是 `發包項目`
5. **不查 `API-query-data-source`**（環境已知會壞），改用 retrieve-a-page 追 relation，或全文搜尋存檔篩選
6. **不觸碰「已收金額」**（業主端收款是另一件事，不在此 skill 範圍，但 YUSHI 銀行收支帳的「收入類」科目已預留，未來可另建 `/業主收款登記` skill 串接業主收款記錄資料庫 `3767aebd-089f-81d8-a4a0-df836a89e70d`）
7. **不建立/修改「本案發包明細」獨立表格**（發包管理的「專案」relation 填對，案件財務管理頁面上的過濾 view 會自動出現該筆，不需要另外寫）
8. **每筆付款都要同步寫入 YUSHI 分錄紀錄**（STEP 5.5），這是銀行收支帳的唯一資料來源，漏記會導致科目餘額對不上實際銀行狀況
9. 跟 `/廠商匯款建檔`（登記廠商銀行帳戶/請款單資料，操作供應商資料庫 `8ed44912-...` 與廠商匯款資料表 `3387aebd-...`）是完全不同的 skill 與資料庫，觸發詞不同（該 skill 觸發於「請款單/發票/匯款資訊」，本 skill 觸發於「廠商匯款/工程匯款/已付款」）
