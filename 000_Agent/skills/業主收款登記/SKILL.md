## 為什麼查詢用存檔篩選、不直接吃 MCP 回傳

跟 `/發包付款登記` 同一個環境限制：`mcp__notion-win__API-query-data-source` 會回 `invalid_request_url`，不要用它查資料庫。`API-retrieve-a-page`、`API-patch-page`、`API-post-page`（parent 用 `data_source_id`）正常可用。`API-post-search` 結果過大時存檔用 `PYTHONIOENCODING=utf-8 python3` 篩選。

**寫入含中文的 JSON 屬性時，一律先用 Write 工具寫成檔案，再用 `curl --data-binary @檔案路徑` 送出**——直接把中文字串塞進 Bash 的 `-d` 參數字串會被 Git Bash 的編碼機制弄亂（曾經把「YUSHI 會計科目表」建成亂碼，事後花時間 archive 重建）。MCP 的 `API-post-page` / `API-patch-page` 工具本身直接傳中文沒問題，只有「透過 Bash 組 curl 指令」這條路徑才會出事。

## 執行步驟

### STEP 1：解析輸入 + 摘要確認 ⭐先摘要再動手

從使用者訊息抓：Notion連結（可能是案件財務管理頁，可能沒有）、案件關鍵字、金額、收款日期（今天/昨天/具體日期，預設當天）、款項類型（開工款/期中款/完工款/追加工程款/其他，沒說就先問或依上下文判斷）。

**支援一次多筆**。

**在做任何 Notion 寫入之前**，先列摘要表格給使用者確認：

| 案件 | 款項類型 | 金額 | 收款日期 |
|---|---|---|---|
| 龍潭1F門面裝修工程 | 期中款 | 210,000 | 2026-07-15 |

使用者確認無誤後才進 STEP 2。

---

### STEP 2：定位業主收款記錄

- 若有連結指向**案件財務管理頁**（`parent.database_id = 2f97aebd-...`）→ 讀該頁「收款紀錄」relation 清單，逐筆 `API-retrieve-a-page` 找「狀態=待收」或「部分收」且金額/類型吻合的既有記錄
- 找到吻合的待收記錄 → 那筆就是目標，進 STEP 3（不要重複建立新記錄）
- 找不到吻合的待收記錄，或使用者只給案件名稱文字沒給連結 → 用案件名稱關鍵字全文搜尋定位案件財務管理頁，同樣先找待收記錄；真的沒有既有排程記錄才建全新一筆
- 找到多筆疑似符合 → 列出來讓使用者選，不自己猜

---

### STEP 3：金額比對——不符一律問，不設容許誤差

若該筆記錄已有「應收金額」，跟使用者說的金額比對：
- **等於應收金額** → 視為全額收訖，狀態訂為「已收」
- **小於應收金額** → 狀態訂為「部分收」，**停下來跟使用者確認**這是分期收款還是金額有誤
- **沒有預設應收金額**（全新建立的記錄）→ 直接採用使用者給的金額，狀態訂為「已收」

---

### STEP 4：更新/建立業主收款記錄

**已有既有記錄**，用 `API-patch-page`：
```json
{
  "實收金額": {"number": {金額}},
  "狀態": {"select": {"name": "已收"}},
  "收款日期": {"date": {"start": "{日期}"}}
}
```

**沒有既有記錄**，用 `API-post-page`（parent 用 `data_source_id: 3767aebd-089f-8171-b60a-000b0ef20205`）：
```json
{
  "說明": {"title": [{"text": {"content": "{案件名稱} {款項類型}"}}]},
  "應收金額": {"number": {金額}},
  "實收金額": {"number": {金額}},
  "狀態": {"select": {"name": "已收"}},
  "類型": {"select": {"name": "{開工款/期中款/完工款/追加工程款/其他}"}},
  "收款日期": {"date": {"start": "{日期}"}},
  "Related to 案件財務管理 (收款紀錄)": {"relation": [{"id": "{案件財務管理page_id}"}]}
}
```

**⚠️ 這個 relation 欄位名稱是 dual-linked 的正確欄位**（跟案件財務管理的「收款紀錄」同步），新建記錄時務必填，否則案件財務管理頁面的「已收金額」rollup 不會更新。

### STEP 5：同步建立 YUSHI 分錄紀錄

```json
{
  "摘要": {"title": [{"text": {"content": "{案件名稱} {款項類型} 收款{金額}"}}]},
  "日期": {"date": {"start": "{日期}"}},
  "交易類型": {"select": {"name": "收入入帳"}},
  "借方科目": {"relation": [{"id": "39e7aebd-089f-8140-b697-ee214fe68a91"}]},
  "借方金額": {"number": {金額}},
  "貸方科目": {"relation": [{"id": "39e7aebd-089f-8101-81bf-fd1994fb4f60"}]},
  "貸方金額": {"number": {金額}},
  "關聯收款紀錄": {"relation": [{"id": "{STEP4的業主收款記錄page_id}"}]},
  "關聯案件": {"relation": [{"id": "{案件財務管理page_id}"}]}
}
```

- 借方科目預設「銀行帳戶」（`39e7aebd-089f-8140-b697-ee214fe68a91`）——使用者說是現金收的，改用「現金」（`39e7aebd-089f-8171-b525-f97f1bdfdb78`）
- 貸方科目固定「工程款收入」（`39e7aebd-089f-8101-81bf-fd1994fb4f60`）——目前不透過「應收帳款」科目沖銷，直接認列收入，做法對稱 `/發包付款登記` 的「直接借記工程款支出」

寫完後可回頭 `API-retrieve-a-page` 確認「銀行帳戶」與「工程款收入」科目的「目前餘額」是否已同步變動。

## 重要規則

1. **先摘要、後動手**：任何 Notion 寫入前，必須先把「案件/款項類型/金額/日期」整理成表格給使用者確認
2. **支援一次輸入多筆**，逐筆各自跑完整 STEP 1~6
3. **優先找既有的「待收」排程記錄更新，不要重複建立**——大部分案件在建案時就已經照合約分期預先建好收款排程
4. **金額不符應收金額一律停下來問**，不設誤差容許範圍
5. **relation 欄位別填錯**：業主收款記錄新建時務必填 `Related to 案件財務管理 (收款紀錄)`，否則案件財務管理的已收金額 rollup 不會同步
6. **每筆收款都要同步寫入 YUSHI 分錄紀錄**（STEP 5），這是銀行收支帳的唯一資料來源
7. **不觸碰「發包管理/已付金額」**（廠商付款是另一件事，屬於 `/發包付款登記` 範圍）
8. 跟 `/發包付款登記` 是方向相反的對稱 skill：本 skill 收入進帳（借銀行/現金、貸收入），對方支出付款（借費用、貸銀行/現金）
