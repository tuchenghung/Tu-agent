# 案件發包與記帳連動優化初稿

## 範圍與依據
2026-09-10 讀取案件財務管理、龍潭1F案件、主發包管理、案件內嵌發包檢視、廠商付款明細 schema，並檢閱報價單輸入資料庫 STEP 8、發包付款登記及 YUSHI 最新專案紀錄。此次為現況盤點與設計，未修改正式帳務、資料庫或 Skill。

## 確認現況
- 建立發包資訊現藏在「報價單輸入資料庫」STEP 8；成本按既有規則填含稅成交金額。
- 龍潭1F頁面有15筆發包關聯；內嵌表格使用主發包管理同一 data source，無需另建發包資料庫。工具回傳該檢視未列出 filter，需再驗證是否只顯示本案，不直接斷言介面已串案。
- 發包管理的工程進度與付款狀態共用「狀態」欄位，缺少獨立付款狀態及未付餘額欄位。
- 廠商付款明細有多個相似 relation，主庫已付金額所依賴的是雙向「Related to 發包管理  (付款明細)」。
- 舊付款 Skill 以本次金額比較總成本，之後直接設已付款；累計分期、重送查重、失敗恢復規則不足。分錄範例缺關聯案件。
- 最新 YUSHI 專案紀錄已記載正式連動、分期分攤、交易 UUID、內容指紋及失敗鎖定；後續應共用既有實作，避免 Skill 再各自建立一套寫入邏輯。本次未稽核程式或正式交易。

## 建議架構
案件財務管理 → 發包管理 → 廠商付款明細 → YUSHI 分錄。
案件財務管理 → 業主收款紀錄 → YUSHI 分錄。
供應商主檔以 relation 連到發包，避免只靠標題辨認廠商。

1. 抽出獨立「廠商發包登記」流程：案件、供應商、工種、成交金額與稅別、報價來源、發包日期、付款條件、追加識別；報價匯入可呼叫同流程，已匯入報價也可直接發包。
2. 發包是合約承諾事件，不能僅因發包就產生實際付款紀錄。實際收付款再走既有 YUSHI 交易流程；認列及沖帳依既有帳務狀態判定。
3. 工程狀態與付款狀態分開。付款狀態依有效累計付款及核定合約額判定未付、部分付、付清或超付待核對；保留款與未到期款另列，不把所有未付都稱逾期。
4. 發包額維持既有含稅欄位相容性；新增稅別、稅額及未稅額需有成交資料佐證。毛利計算稅基需查公式後再核定，不能直接套歷史除1.05公式。
5. 本案頁正文固定有發包、業主收款與付款明細檢視，以本案 relation 篩選。優先修正 linked view，避免用手工表格維護第二份金額。
6. 查重使用穩定操作識別與來源報價／版本，不以同案件同廠商直接認定重複；允許不同工項及追加。收付款來源明細與分錄要能互相追溯。

## 案件總覽建議
合約總額、已收、未收、已發包合約額、廠商已付、合約未付、案件現金收支淨額。毛利與現金收支分開呈現；到期應收應付須有請款／付款排程作依據。

## 實施順序與驗收
1. 以龍潭1F盤點15筆發包的付款明細、案件關聯及分錄；解析 rollup/formula 後列差異，不用勾選框推定已付金額。
2. 核對案件頁篩選、公式及新版 YUSHI 欄位契約，列出新增欄位與相容性調整。
3. 先完成獨立發包入口與共用流程，再調整付款 Skill。既有欄位不先刪除或更名。
4. 使用隔離資料驗證新發包、同廠商追加、訂金加尾款、合併付款、重送及中途失敗；正式款項不得當测试交易。
5. 驗收：一次發包只有一筆主資料、案件頁立即可見；付款累計等於有效付款明細，對應分錄與案件合計一致；重送不重複入帳。
