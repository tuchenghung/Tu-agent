# 財務程式隔離盤點

盤點日期：2026-09-10。範圍：`yushi-finance` 指定 Notion 存取、報表、API、runtime、測試及其引用的 D1 migration。唯讀檢查程式，僅新增本報告；未讀取 `.env`、未連線正式 Notion、未修改程式、未執行正式交易。以下行號以本次工作區版本為準。

## 結論

**目前程式是固定單一資料來源的 YUSHI 財務工作台，尚未具備可驗證的 YASHI／YUSHI 與宏祐多集團隔離能力。** 本次能證實程式缺少集團／公司／帳本限定，不能據此宣稱正式 Notion 已混帳。既有單帳本的驗證、重送防護與不確定寫入鎖有實作，但不等於兩集團隔離。

## 測試現況與證據界線

- `tests/finance.test.mjs:7–12` 將指定 TS 模組轉譯後測試，runtime 用測試環境替代；`:49–94` 是單份合成帳本資料。API 測試使用 synthetic token 與 mock fetch（`:144–160,228–253,270–275`）。不能證明正式連線與資料權限正確。
- 已有跨案／超付／未知餘額拒絕、付款與收款連動、重送防護、未授權拒絕、部分寫入保留鎖、報表及轉帳檢查案例（`:97–160,171–216,255–275`）。本次僅讀取案例，未重跑，不能把案例存在寫成測試通過。
- 全部測試未建立兩集團／兩公司／兩帳本 fixture，未測跨帳本 ID 注入、混合帳本報表、另一集團餘額不變、鎖互不干涉、帳本範圍冪等與操作紀錄授權。
- 未證實：六個 DS 的正式內容與集團歸屬、Notion relation／rollup 是否連到外集團、integration 實際存取範圍、宏祐是否已另有獨立財務 DB／D1／部署、既有資料是否已混用、正式發布版本是否與工作區相同。需另做唯讀盤點。

## 最新範圍修正與驗收

使用者明確澄清：只處理 YASHI／YUSHI 帳目，宏祐帳務不納入。因此前述多帳本缺口只是原盤點觀察，不是必須建置的功能；不建立宏祐帳本、不拆雙部署、不新增跨帳本鎖。

現階段只需保留單帳本架構並補足案件來源驗證：Projects 已有集團與公司別，主代理查到15筆案件財務皆指向YUSHI專案。未見混帳證據；詳見工程管理SOP_資料關聯盤點.md。

1. 有案件的記帳操作須解析案件財務→Projects唯一關聯，確認集團YUSHI；宏祐、缺值、多重或矛盾關聯一律在外部寫入前拒絕。
2. 不把一般無案件的公司費用強迫掛虛構案件；科目與帳戶仍限定既有YUSHI資料來源。
3. 保留原單帳本鎖、重送去重與needs_review機制；宏祐工程管理不接此財務入口。
4. 使用合成測試資料驗證YUSHI正常交易、宏祐誤掛、未知歸屬及關聯衝突；不以正式帳務試寫。本次未修改程式、未執行驗收。
